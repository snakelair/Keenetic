# 📦 Smart-Photo Changelog

## [1.0.54] - 2026-09-12

### Deep RAM Optimization Phase 2: Dynamic Path Slicing, Compact DB Streaming, Heap De-duplication & Zero-Copy Timelines
- **Динамический срез имени файла (`Photo.FileName()`)**:
  - Поле `FileName string` полностью удалено из структуры `Photo`, экономя 16 байт заголовка строки + длину имени файла в куче на каждый объект каталога (~3.4 МБ постоянной RAM при 85 000 фото).
  - Метод `FileName()` вычисляет имя файла на лету через срез существующей строки `RelPath` без единой аллокации в куче.
  - Сохранена 100% обратная совместимость с API и Web UI через динамический `Photo.MarshalJSON()` / `Photo.UnmarshalJSON()`.
- **Исключение уникальных идентификаторов из `internMap`**:
  - Уникальный хэш `Photo.ID` исключен из глобальной карты интернирования строк: так как ID гарантированно уникален для каждого файла, сохранение 86 000 уникальных ключей в мапе приводило к паразитному расходу ~7–8 МБ RAM при нулевом проценте повторений.
  - Размер `internMap` ограничен лимитом в 8192 записей с фильтром по длине строки (<= 256 символов) для надежной защиты от утечек памяти.
- **Потоковая генерация и отдача `compact_db.json.gz`**:
  - Полностью исключено хранение сжатого буфера `compactGzCache []byte` в оперативной памяти (экономия до 5 МБ постоянной RAM).
  - Сжатый индекс `compact_db.json.gz` стримится напрямую в файл на внешний диск и отдается клиентам через `http.ServeContent` с использованием эффективного файлового кэша ядра Linux (Page Cache).
- **Zero-Copy таймлайн (`TimelineDayGroup.Photos []*Photo`)**:
  - В срезе фото таймлайна `TimelineDayGroup.Photos` заменены тяжелые структуры (120+ байт) на компактные указатели `[]*Photo`.
  - Устранено постоянное копирование сотен килобайт данных по значению при каждом HTTP-запросе таймлайна.
- **Оптимизация бакетов сводки таймлайна**:
  - Внутренние ключи группировки месяцев в `recomputeCachedSummariesLocked` переведены с форматированных строк (`"2026-08"`) на быстрый целочисленный ключ `int` (`year*100 + month`), предотвратив 85 000 строковых аллокаций во время сканирования.

## [1.0.53] - 2026-09-12

### High-Performance RAM Optimization, Streaming Index Loading, Lazy EXIF & Adaptive Memory Tuning
- **Потоковая загрузка индекса без промежуточных срезов (`StreamIndex`)**:
  - Чтение `index.json.gz` переведено на потоковый токенайзер `json.Decoder.Token()` / `dec.More()`.
  - Элементы каталога десериализуются по одному и сразу размещаются в целевых структурах `map` и срезе.
  - Полностью устранён пиковый всплеск потребления памяти (memory spike) при старте сервиса, снизив пик RAM при перезапуске на 60%.
- **Облегчение структуры `Photo` и оптимизация выравнивания памяти**:
  - Устранено мертвое строковое поле `FullPath` (путь разрешается на лету через `GetEffectiveFullPath`).
  - Устранено поле `AspectRatio float64` (рассчитывается на лету `Width / Height`), давая выигрыш в 8 байт на каждое фото.
  - Упорядочены поля структуры для минимизации байтового паддинга компилятора, булевы флаги плотно упакованы в битовую маску байта.
  - Добавлено сквозное интернирование идентификатора `ID = Intern(ID)`: ключи мап, списки и метаданные используют общий указатель на срез байт в куче.
- **Ленивый EXIF и очистка пустых метаданных**:
  - Добавлен метод `ExifData.IsEmpty()`: для изображений без метаданных (PNG, WebP, видео, JPEG без EXIF) память под структуру больше не выделяется (`nil`).
  - В `GetPhotoDetails` реализован метод `GetPhotoWithDetails`: при клике по фото подробные параметры съемки (линза, выдержка, ISO, GPS) мгновенно считываются из первых 64 КБ файла на диске, не занимая оперативную память в покое.
- **Пул буферов `sync.Pool` и оптимизация поворотов превью**:
  - Внедрён пул `sync.Pool` для `bytes.Buffer` в генераторе миниатюр, предотвращая частые реаллокации при JPEG-сжатии.
  - Оптимизирован `applyOrientation`: поворот на 180° и отражения выполняются по месту (in-place swap пикселей) без выделения второго полного растрового буфера `image.RGBA`.
- **Адаптивный аппаратный тюнинг памяти под роутеры (`GOMEMLIMIT`)**:
  - Интегрирована функция `GetRecommendedMemoryLimit()`: сервис анализирует `/proc/meminfo` и автоматически выставляет лимит кучи Go:
    - 36 МБ для роутеров со 128 МБ RAM (Keenetic City, Air, Extra);
    - 64 МБ для роутеров с 256 МБ RAM (Keenetic Speedster, Giga III);
    - 96 МБ для роутеров с 512 МБ RAM (Keenetic Ultra, Titan, Hero);
    - 160–256 МБ для серверов и ПК.
  - Значение `MemCacheSizeMB` оптимизировано по умолчанию до 2 МБ, передавая управление кэшем файлов системному Page Cache ядра Linux.

Финализация выгрузки (`handleCompleteUpload`) на роутере выполняется мгновенно (~0 мс) без повторного медленного чтения файла целиком с USB-диска, исключая таймауты сокетов.
  - **Поддержка параметра offset и дозаписи**: в API передачи фрагментов (`/upload/{session_id}/chunk?offset=...`) добавлена точная позиция смещения `f.Seek()`, позволяющая клиенту повторять отправку сбойных чанков.
  - **Автоматические повторы (Retries) в Android-клиенте**: в `ChunkedUploader` реализован цикл до 3 попыток отправки каждого чанка и финализации сессии с нарастающей паузой при сбоях Wi-Fi.
  - **Увеличение таймаутов HTTP**: таймауты чтения и записи в OkHttp (`ApiClient.kt`) и на сервере увеличены со 120s до 180–300s.
  - **Асинхронная индексация**: немедленный ответ клиенту об успешной выгрузке, фоновая генерация превью и добавление в индекс без блокировки сетевого соединения.
- **Защита от параллельного запуска нескольких синхронизаций (Race Conditions)**:
  - **Мьютекс на уровне репозитория (`SyncRepositoryImpl`)**: добавлен `Mutex.tryLock()` — любые повторные запросы синхронизации отсекаются с предупреждением в лог, пока идёт текущий процесс.
  - **Блокировка повторных нажатий в UI (`SettingsViewModel`, `GalleryViewModel`, `SettingsScreen`)**: кнопка «Синхронизировать сейчас» отключается во время активного процесса синхронизации, методы запуска проверяют активность корутины.
- **Таргетированное сканирование изменённых директорий (FSWatcher)**:
  - **Локальное сканирование папки при изменениях**: при возникновении событий создания, изменения или удаления файлов демон теперь сканирует **только ту директорию**, в которой произошли изменения (`ScanDirectory`), не обходя остальные папки библиотеки. Это кардинально снижает нагрузку на CPU роутера и ускоряет реакцию на добавление/удаление фото.
  - **Корректное удаление файлов из галереи**: при удалении файлов или каталогов удалённые медиафайлы вычищаются из индекса на лету, сохраняя неизменными все остальные папки.
  - **Полное периодическое сканирование сохранено**: фоновое плановое сканирование по таймеру (`scan_interval_minutes`), первичное сканирование при старте и ручное сканирование через API остаются **полными**, гарантируя 100% целостность библиотеки.
